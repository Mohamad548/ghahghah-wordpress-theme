### Browser diagnosis (PO before nav)

| Probe | `isMobile` | LCP entries | Notes |
|-------|------------|-------------|-------|
| 390×844 default | `true` | **0** | Matches LH mobile failure mode |
| 390×844 default | `false` | **≥1** (hero `<img>`) | Compatible method |
| 390×844 + `deviceScaleFactor:2.625` | `false` | **0** | DPR high also breaks PO here |
| 390×844 + `prefers-reduced-motion: reduce` | `true` | hero LCP | Motion preference interacts with mobile emulation |
| 1440 desktop | `false` | hero LCP | Works |

**Proven tooling interaction:** Chrome **mobile emulation** (`isMobile: true` / LH screenEmulation.mobile) yields **no LCP entries** on this homepage in lab, even when the active hero image is decoded and visible (`opacity:1`, `visibility:visible`). Same CSS at 390×844 **without** mobile emulation reports LCP on `img.ghahghah-hero__image`.  

First slide already had `is-active` + `fetchpriority="high"` in HTML — **not** “hidden first slide” or “multiple high inside Hero” as the NO_LCP root cause.

Isolation also showed: aborting `hero.js` + forcing `transition:none` does **not** restore LCP under `isMobile:true`. Desktop-sized PO and non-mobile 390 PO do.

### Loading competition (production-relevant)
